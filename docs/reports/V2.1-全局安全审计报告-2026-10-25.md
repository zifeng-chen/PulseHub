# FAM V2.1 全局安全审计与漏洞检查报告

**审计日期**：2026-10-25
**审计范围**：`backend/app`（82 个 Python 文件，约 28,000 行）+ `frontend/src`（102 个 Vue/TS 文件，约 29,000 行）+ 部署配置（Nginx / Docker / compose）
**审计方式**：静态源码审查 + 自动化脚本扫描（鉴权覆盖率、家庭归属校验、SQL 注入、敏感信息泄露、依赖完整性）+ 后端测试套件全量运行
**测试结果**：**262 项后端测试全部通过（100%）**，无回归。

---

## 一、总体结论

这是一套**安全基础打得相当扎实**的家庭财务系统。以下维度经过核查属于「做对了」：

- **SQL 注入**：全部走 SQLAlchemy ORM，原生 `text()` 仅 3 处（`SELECT version_num`、`SET FOREIGN_KEY_CHECKS`）且无用户输入拼接，**零注入面**。
- **认证链路**：bcrypt(12 rounds) 密码哈希、短时 access token + 可撤销 refresh token（单次轮换）、连续失败锁定、会话表 + 撤销机制，均正确。
- **越权防护（服务层）**：账户/资产/负债/投资/租赁/附件/OCR 等核心领域对象在 `get_*` 入口统一做 `household_id` 归属校验，抽查均正确。
- **二次确认**：删除/冲销/启用外发等高影响动作走一次性 JWT 令牌（jti 黑名单防重放 + 5 分钟时效），实现严谨。
- **敏感信息**：密钥/口令 Fernet 加密落库、展示只给掩码、日志 `scrub()` 递归脱敏、审计 `SENSITIVE_FIELDS` 白名单、生产环境密钥自检（缺密钥拒绝启动）。
- **前端 XSS**：全仓 **0 处** `v-html` / `innerHTML` / `eval` / `document.write`，Nginx 配了 CSP。
- **上传安全**：扩展名 + MIME + 魔数三重校验 + 大小限制 + SHA256，落盘按家庭隔离、文件名不暴露原始名。
- **金额精度**：后端 `Decimal` + 统一 `fmt_amount`，金额字段全部 `Numeric`（无 Float），无浮点金额存储。

**真正的短板不在「单点漏洞」，而在三类系统性缺陷**：① 认证失效链路的状态机；② 业务规则泄漏到前端；③ 请求时序/下载的基建不一致。以及若干**中等风险的家庭归属校验遗漏**（配置表 + 审计详情）。

## 二、高危问题（🔴 阻塞级，建议优先修复）

### 🔴 B-1　锁屏输错密码 = 整个会话被销毁（会触发死循环）
- **位置**：`backend/app/api/v1/auth.py:84-85` + `frontend/src/api/client.ts:126-135` + `frontend/src/stores/auth.ts`
- **问题链**：锁屏解锁接口 `/auth/verify-password` 密码错误时返回 **401**（`AppError(FORBIDDEN, "密码不正确，请重试", status_code=401)`）。而前端 axios 拦截器把所有 401 一律当作「会话过期」→ `tokenStore.clear()` + 跳登录页。
- **后果**：用户锁屏后手滑输错一次密码 → 本地 token 被删 → 被踢去登录。而代码注释（`AppShell.vue`）明确写着「锁屏：只遮住界面，不动会话」。
- **建议**：`request()` 里把 `/auth/verify-password`（以及 `/auth/login`）加入「不触发全局 401 处理」的白名单；或后端此接口改用 403/422 返回（语义本就是「密码不对」，不是「未认证」）。

### 🔴 B-2　401 只清 token 不清 `auth.user`，会话过期后死循环进不了登录页
- **位置**：`frontend/src/main.ts:15-19`、`frontend/src/api/client.ts:132-135`、`frontend/src/stores/auth.ts:37-40`、`frontend/src/router/index.ts:53-59`
- **问题**：`onUnauthorized` 只 `router.push('/login')`，清了 localStorage 但 `auth.user` 仍是旧对象、`auth.loaded` 仍是 `true`。守卫判「已登录」又把用户弹回 `/dashboard`，AppShell 再请求 401 → 再跳登录 → **无限往返，每轮都发请求**。用户只能手动刷新浏览器脱困。
- **建议**：把 401 收口成 `forceLogout()`：`tokenStore.clear(); auth.user=null; auth.loaded=true; router.replace('/login')`；守卫的 `isAuthenticated` 改为「有 user 且有 access token」双重判断。

### 🔴 B-3　跨标签页/重复刷新互相作废 refresh_token，双开窗口对账直接掉登录
- **位置**：`frontend/src/api/client.ts:75-96`（tryRefresh 单例）+ `frontend/src/stores/auth.ts:57-70`（loadMe 无条件 refresh）+ `frontend/src/App.vue:71-74`（又刷一次）
- **问题**：后端 refresh 是**单次使用轮换**（`auth.py:148-153` 每次覆写 `refresh_token_hash`）。前端去重只覆盖「同页并发」，跨标签页各拿同一个 refresh token 调 `/auth/refresh`，后到者 hash 不匹配 → 401 → 清空 localStorage，把先到者刚写的新 token 也删了。
- **放大**：守卫 `loadMe()` 刷一次 + `App.vue` 挂载又刷一次，整页刷新即轮换两次。
- **建议**：① `loadMe` 改成「access 未过期只调 `/auth/me`，仅 401 才 refresh」；② 删 `App.vue` 重复 loadMe；③ refresh 加跨标签互斥（localStorage 锁 + BroadcastChannel）；④ refresh 失败时不要立刻 clear，先比对失败用的 token 是否已被别的上下文换过。

### 🔴 B-4　对账页切账户无请求序号，旧预览覆盖新账户 → 可能写错账
- **位置**：`frontend/src/views/ledger/ReconciliationView.vue:57-92`
- **问题**：`loadPreview()` 无 `loadSeq`/AbortController，`actualBalance` 无条件赋值。快速切账户时慢响应回写，把「招行余额」当成「工行余额」提交对账，生成金额错误的调整事件，直接改动账户余额与统计。
- **建议**：加 `++loadSeq` 序号守卫；`submit()` 提交 `account_id` 让后端校验一致性；对账提交前禁用账户选择器。

### 🔴 B-5　「云端外发总开关」能开不能关，但界面提示「已更新」
- **位置**：`frontend/src/views/settings/SettingsPrivacyView.vue:54-58`（关闭分支）+ `90-98`（save 未带该字段）
- **问题**：关闭只改本地 `form`，`save()` 的 PUT body **不含** `cloud_egress_enabled`；后端 `settings.py:828` 字段缺失即不变，随后 `load()` 拉回「开」。**这是安全开关实质失效**，用户会误以为已停止外发。
- **建议**：关闭时单独 `PUT { cloud_egress_enabled: false }`（关闭无需 confirm_token），成功后刷新。

### 🔴 B-6　负债「每期应还」由前端 JS 算出并写库，后端优先采信
- **位置**：`frontend/src/views/ledger/LiabilitiesView.vue:393-434` + `backend/app/services/liabilities.py:786`
- **问题**：前端用 `(principal*rate*(1+rate)^n)/((1+rate)^n-1)` 等额本息，`toFixed` 后作为业务事实提交，后端直接落库不重算。JS double + `toFixed`（二进制舍入）与后端 Decimal 结果可能在分位差 1，360 期放大挤进末期；等额本金直接拿「首期最大额」写进单一 `monthly_payment`，月供汇总与现金流预测被高估。
- **建议**：删 `computedPayment` 的写库路径，改为只读参考；提交本金/利率/期数/方式，由后端算完回填（后端已有函数）。**存量已写入的数据需一次回算脚本**。

## 三、中危问题（🟡 应修复）

### 🟡 M-1　配置表按 id 取单条未做家庭归属校验（IDOR）
- **位置**：`backend/app/api/v1/settings.py:717/757/779`（`ThirdPartyAIProvider` 按 id）、`backend/app/api/v1/settings.py:243`（`HouseholdMember` 按 id，但紧接校验了 household_id，安全）
- **问题**：`update_provider` / `egress_preview` / `delete_provider` 三个端点用 `select(ThirdPartyAIProvider).where(id==provider_id)` **未加 household_id 过滤**。已知 provider_id 时，A 家庭的管理员可越权读/改/删 B 家庭的第三方 AI 配置（含 base_url 与掩码 key）。
- **说明**：这些端点都有 `require_action(user, "configure")` 挡着，普通成员进不来；但「configure 权限」是家庭级，跨家庭仍成立。单家庭部署（当前 M0）实际风险低，多家庭扩展前必须补。
- **建议**：统一加 `ThirdPartyAIProvider.household_id == user.household_id`。

### 🟡 M-2　审计详情接口未做家庭归属校验
- **位置**：`backend/app/services/audit.py:193-202`（`audit_detail` 按 id 取，无 household 过滤）+ `backend/app/api/v1/audit.py:32-40`
- **问题**：`GET /audit/{log_id}` 已知 log_id 即可读任意家庭的审计详情（含字段级变更前后值）。入口有 `require_action("audit_view")`（默认仅 owner/admin），但仍构成跨家庭 IDOR。
- **建议**：`audit_detail` 增加 `household_id` 参数并过滤；或把校验下沉到 service。

### 🟡 M-3　第三方 AI 供应商的 GET 接口不校验 action，成员可读配置
- **位置**：`backend/app/api/v1/settings.py:635`（`list_providers` 无 `require_action`）
- **问题**：任何家庭成员（含 readonly）都能读到 `base_url`、`default_model`、`api_key_masked` 等配置信息。
- **建议**：`list_providers` / `egress_preview` 等 GET 加 `require_action(user, "configure")`，或明确产品是否允许成员只读。

### 🟡 M-4　贝壳估价/测试接口存在 SSRF 面（低概率）
- **位置**：`backend/app/services/beike.py:82-88 / 196-214` + `backend/app/api/v1/settings.py:582`（`put_beike` 可配 base_url）
- **问题**：`base_url` 由管理员配置，`assess_price`/`test` 用它拼 `httpx.post(f"{base}/...")`。若管理员配了内网地址，后端会向内网发请求。
- **说明**：能改 base_url 的人本就有 `configure` 权限（家庭管理员），且这是家庭自建部署，实际风险低。
- **建议**：保存 base_url 时校验为 http(s) 且 host 在白名单（或至少不允许私网网段）；对外发调用统一加超时与响应体大小上限。

### 🟡 M-5　`decimal_str()` 用 float 转字符串，金额精度有隐患
- **位置**：`backend/app/core/ids.py:48-55`
- **问题**：`decimal_str` 用 `f"{float(value):.{places}f}"`，float 二进制转换对 `Decimal` 大数/高精度会失真。当前无调用方（grep 仅定义处），属于「隐患而非现患」。
- **建议**：改为 `Decimal(str(value)).quantize(...)` 或直接删掉死函数。

### 🟡 M-6　`delete_provider` 用硬删除，与全系统软删除约定不一致
- **位置**：`backend/app/api/v1/settings.py:781`（`await db.delete(provider)`）
- **问题**：其余业务对象（账户/资产/负债/附件）均软删除保留审计；此处物理删除，撤销后无法追溯该供应商的历史外发审计关联。
- **建议**：改为软删除（`deleted_at` 标记）。

### 🟡 M-7　CSV 导入未做公式注入防护
- **位置**：`backend/app/services/imports.py:51-56`
- **问题**：`csv.DictReader` 解析后字段直接进草稿事件。若用户导入的 CSV 单元格以 `=` / `+` / `-` / `@` 开头（如 `=cmd()`），未来若导出/在表格软件打开可能触发公式注入。当前数据只落库不导出为 CSV，风险低。
- **建议**：对文本字段做前导 `= + - @` 的转义（加 `'` 前缀）或校验拒绝。

## 八、修复优先级建议（Top 5）

1. **修 401 状态机（B-1 + B-2）**：`forceLogout()` + `/auth/verify-password` 白名单。半天工作量，收益最大——唯一「日常操作就触发、且把用户锁死在门外」的缺陷。
2. **修复 refresh 轮换（B-3）**：`loadMe` 改懒刷新 + 删重复 loadMe + 跨标签互斥。家庭财务「双窗口对账」是高频场景。
3. **修隐私开关（B-5）**：关闭时单独发 `cloud_egress_enabled:false`。10 行以内，但涉及安全承诺。
4. **修对账竞态（B-4）**：加请求序号 + 提交校验。10 行以内，避免写错账。
5. **月供计算权还给后端（B-6）**：删前端写库路径 + 存量数据回算。影响还款计划/月供/现金流三处。
