## 三、发现明细

### H-1【高】上传组件 python-multipart 0.0.20 存在多个可利用的 DoS

**位置**：`backend/requirements.txt`

**证据**：OSV 按版本 0.0.20 检索到 7 个独立问题（14 条记录，含 PYSEC/GHSA 重复），全部修复于 0.0.26–0.0.31：

| 编号 | 问题 | 修复版本 |
|---|---|---|
| GHSA-mj87-hwqh-73pj | multipart preamble/epilogue 过大导致 DoS | 0.0.26 |
| GHSA-pp6c-gr5w-3c5g | part 头无上限导致 DoS | 0.0.27 |
| GHSA-5rvq-cxj2-64vf | 分号分隔的 query 解析二次复杂度（CPU DoS） | 0.0.30 |
| GHSA-6jv3-5f52-599m | 分号被当作字段分隔符导致参数走私 | 0.0.30 |
| GHSA-vffw-93wf-4j4q | Content-Disposition RFC 2231/5987 参数走私 | 0.0.30 |
| GHSA-v9pg-7xvm-68hf | 负 Content-Length 导致整个 body 进内存 | 0.0.31 |
| GHSA-wp53-j4wj-2cfg | 非默认配置下任意文件写 | 0.0.22 |

**为什么是本项目的高危**：附件上传（`POST /ledger/capture/attachments`）走的就是 multipart 解析，任何**已登录的家庭成员**都能构造恶意请求打满 CPU 或内存。本项目部署在 NAS 上、资源有限，一次请求即可拖垮整个家庭实例。

**修复**：升级到 `python-multipart==0.0.32`（已做，全量测试通过）。

### M-1【中】`/setup/summary` 未认证泄露管理员账号与家庭名 —— 线上确认可利用

**位置**：`backend/app/api/v1/setup.py`（原实现无任何鉴权）

**证据**（修复前对线上实例直接请求，未带任何凭证）：

```
GET http://192.168.100.110:18080/api/v1/setup/summary
{"success":true,"data":{"initialized":true,
 "admin":{"username":"陈子疯","display_name":"陈子疯"},
 "household":{"name":"MyHome","base_currency":"CNY","timezone":"Asia/Shanghai"}, ...}}
```

**影响**：任何能访问 18080 端口的人（局域网内、或端口被映射到公网时任何人）都能拿到：管理员登录账号、家庭名称、各外部服务配置状态。这是典型的**侦察信息**——知道用户名后，配合「无速率限制」（见 M-6）可做定向爆破。

**修复**：初始化完成后，匿名请求只返回 `initialized` 与服务状态，`admin`/`household` 置空并标 `redacted: true`；登录用户仍可拿到完整内容。前端完成页改为优先显示向导里已填的值，体验不受影响。

### M-2【中】系统状态接口绕过 `audit_view` 权限返回审计记录

**位置**：`backend/app/api/v1/settings.py` · `GET /settings/system`

**问题**：审计专用接口 `GET /audit` 要求 `audit_view` 动作（仅 owner/admin），但 `/settings/system` 顺手把「最近 10 条审计」塞进返回值，任何登录用户（含 `readonly`）都能看到谁在什么时候改了什么。

**影响**：权限模型形同设了两个门，其中一个没锁。只读成员能看到家庭成员的敏感操作记录。

**修复**：仅当用户具备 `audit_view` 时才返回 `recent_audit`，否则返回空数组且 `audit_total: null`。

### M-3【中】无家庭归属的账号可跨家庭读取审计与备份

**位置**：`backend/app/services/audit.py`（列表、详情）、`backend/app/services/backup.py`（列表、单条）

**问题**：四处都用「条件式过滤」：

```python
conditions = []
if household_id:                      # ← 为空就完全不过滤
    conditions.append(AuditLog.household_id == household_id)
```

而 `_resolve_user` 在用户**没有 active 成员关系**时会把 `household_id` 置为 `None`（成员被移出家庭后账号仍可登录）。此时：

- `GET /audit` → 返回**所有家庭**的审计列表
- `GET /audit/{id}` → 按 id 直读**任意家庭**的审计详情（含字段级差异，可能含金额）
- `GET /settings/backup` → 列出**所有家庭**的备份记录
- `GET /settings/backup/{id}` → 原写法 `if record.household_id and record.household_id != user.household_id` 在备份记录本身没有家庭归属时**整个跳过校验**，任何登录用户可下载全库备份

**修复**：四处的语义统一改为 fail-closed —— 没有家庭归属就返回空/403，绝不退化成「查全部」。

### M-4【中】修改成员角色不做枚举校验（提权口子）

**位置**：`backend/app/api/v1/settings.py` · `PATCH /settings/members/{member_id}`

**问题**：新增成员时校验了角色（`if role not in ("owner", "admin", "member", "readonly")`），修改时却直接写库：

```python
if "role" in payload and payload["role"]:
    member.role = payload["role"]      # ← 可以传 "owner" 或 "superuser"
```

**影响**：① 可写入任意字符串形成脏数据；② 有 `configure` 权限的 admin 可把自己或他人改成 `owner`。当前 owner 与 admin 默认权限集相同，所以实际危害有限，但一旦将来给 owner 加专属能力（如转让家庭、删除家庭），这里就是现成的提权通道。

**修复**：抽出 `MEMBER_ROLES` / `MEMBER_STATUSES` 到 `services/permissions.py`，新增与修改共用同一套枚举校验。

### M-5【中】备份恢复是全表清空，没有家庭维度隔离

**位置**：`backend/app/services/backup_data.py` · `load_database()`

**问题**：

```python
for table in reversed(Base.metadata.sorted_tables):
    await db.execute(table.delete())        # ← 清空所有家庭的全部业务表
```

**当前不可利用**：`POST /settings/backup/{id}/restore` 只创建一条 `RestoreRecord`（status=preview），**没有调用 `load_database`**——恢复执行入口还没接上。

**为什么仍然要报**：这是埋着的雷。代码已存在，注释写着「调用方负责快照/回滚」，而没有任何调用方。将来接上入口时，一个有 `configure` 权限的家庭 owner 恢复备份，就会清掉**其他所有家庭**的数据。

**修复**：在 `load_database` 入口加 fail-closed 断言——检测到多于一个家庭直接拒绝执行，并在文档字符串中写明「这是全库恢复，仅适用于单家庭部署」。

### M-6【中】缺少全局速率限制，登录可被慢速爆破/账号枚举 —— **已修复**

**位置**：全局（`app/middleware/` 只有 context 与 maintenance 两个中间件）

**问题**：

- 登录有**账号级**失败锁定（5 次 / 5 分钟），且不区分「账号不存在」与「密码错」——这两点做得对
- 但**用户名不存在时不计数**，所以攻击者可以无限次枚举用户名（每次都是全新用户名，永不触发锁定）
- 除登录外，任何接口都没有频率限制

**修复**：新增 `app/middleware/rate_limit.py`，按**来源 IP**做滑动窗口计数：

| 类别 | 阈值 | 说明 |
|---|---|---|
| 登录 / 刷新 / 解锁 | 10 次/分钟/IP | 唯一「猜对就能进来」的入口，收得最紧 |
| 其他接口 | 300 次/分钟/IP | 防脚本刷接口耗尽 NAS 资源 |
| `/health` | 不限 | 容器健康检查每 30 秒一次，被限流会被判不健康而重启 |

设计上的三个约束（写在模块文档里）：

1. **限流不能自己把服务拖垮**：桶数量上限 20000，超了先清理，再超就**放行**而不是拒绝——内存耗尽比限流失效严重得多；
2. **阈值每次请求从 settings 读**，不缓存进实例，否则改配置不生效；
3. **429 走统一信封 + `Retry-After`**，且放在 CORS 内层，保证浏览器能看到错误而不是「网络错误」。

**注意**：计数是**进程内**的。单容器单 worker 够用，但扩到多 worker 后每个进程各算一份，实际阈值会被放大 N 倍——届时必须换共享存储。这条已写在模块注释里。

**验证**（线上实测）：连发 13 次错误登录，前 10 次 `401`、第 11 次起 `429`；带 `Origin` 头时 429 也返回 `access-control-allow-origin`。

### L-1【低】锁屏解锁接口无失败计数

**位置**：`app/services/setup.py` · `save_local_ai` / `save_ocr`

### L-7【低】审计日志里的 IP 不是真实来源 —— **已修复**

**位置**：`app/middleware/context.py` · `_ip_summary()`

**证据**：修复前，从局域网机器访问线上站点，日志记录的是

```
"path": "/api/v1/setup/status", "ip": "172.27.0.x"
```

`172.27.0.x` 是 nginx 容器的 Docker 内网地址，不是发起请求的 `192.168.100.x`——因为 `_ip_summary()` 取的是 `request.client.host`，没有读 nginx 已设置的 `X-Forwarded-For`。

**影响**：

1. 审计日志的 IP 字段**失去溯源价值**——所有外部请求看起来都来自同一个容器地址；
2. **这也是 M-6 限流的前置条件**：按错误 IP 限流，全家人共用一个计数桶，一个人刷爆就全家被锁。

**修复**：新增 `app/core/netutil.py`，把解析规则做成纯函数（可单测）：

- 直接对端**不在**可信代理范围 → 用它，忽略 `X-Forwarded-For`（否则任何人都能伪造来源）；
- 直接对端**在**可信代理范围 → 取 XFF 的**最后一项**。nginx 用 `$proxy_add_x_forwarded_for` 把真实对端追加在末尾，前面都是客户端自己填的，取前面等于让攻击者自己报 IP；
- 末项不是合法 IP → 退回直接对端，不把脏值写进审计。

**信任范围默认只给** `127.0.0.1,::1,172.16.0.0/12`（本机 + Docker 内网），**故意不含** `192.168.0.0/16`：局域网机器能直连 18000 端口，若把整个私网都当代理，它们就能伪造头绕过限流。部署指南里补了这一条与对应的排障项。

**验证**（线上实测）：同一请求的日志从 `172.27.0.x` 变为 `192.168.100.x`。

## 四、依赖漏洞逐条判断

OSV 按实际版本返回的记录数很多，但**能不能打**取决于用没用到受影响的功能：

| 包 | 原版本 | 记录数 | 可用性判断 | 处理 |
|---|---|---:|---|---|
| python-multipart | 0.0.20 | 14（7 个独立问题） | **可利用**：附件上传路径直接命中 DoS | 升 0.0.32 |
| PyJWT | 2.10.1 | 32（约 17 个独立问题） | **基本不可利用**：绝大多数是 `PyJWKClient`（拉 JWKS）、非对称公钥当 HMAC 密钥、PEM 解析 ReDoS；本项目只用 **HS256 + 自己生成的对称密钥**，没有公钥、不拉 JWKS。但版本落后 5 个小版本，暴露面随功能演进会变化 | 升 2.15.1 |
| cryptography | 44.0.0 | 12 | **基本不可利用**：问题集中在 X.509 路径构建、PKCS#7、SECT 曲线、DNS 约束；本项目只用 `Fernet`（AES-CBC + HMAC）。其中「wheels 内置 OpenSSL 漏洞」与 Fernet 无直接关系 | 升 50.0.2 |
| aiomysql | 0.2.0 | 2（同一问题） | **不可利用**：需攻击者控制 MySQL 服务端才能触发；本项目连自家 NAS 的 MySQL | 升 0.3.2 |
| fastapi / uvicorn / SQLAlchemy / httpx / bcrypt / alembic / pydantic / PyMySQL / aiosqlite | — | 0 | — | 不动 |

**升级后验证**：Fernet 往返、JWT 签发/校验、篡改拒绝（`DecodeError`）、过期拒绝（`ExpiredSignatureError`）全部正常；后端全量测试（含新增 8 个安全用例）通过。

PyJWT 2.15 新增了一条 `InsecureKeyLengthWarning`：测试环境用的 `FAM_JWT_SECRET` 只有 15 字节。生产是 64 字节，合规；测试密钥短不影响正确性，但如果想消除告警，可把 conftest 里的测试密钥加长。

## 六、做得好的部分（不要改坏）

1. **密码**：bcrypt 12 轮；登录失败 5 次锁定；不区分账号不存在与密码错（防枚举）
2. **会话**：access 30 分钟 / refresh 滑动续期；session 存库可撤销；改密/停用成员会撤销全部会话
3. **信任边界**：`household_id` 从**成员关系**查，不信 token 里的 `hh`——篡改 token 也跨不了家庭
4. **归属校验**：所有按 id 取单条的地方都是「查出来再比 household」，`accounts` / `assets` / `attachments` / `card_bills` 等一致
5. **上传**：扩展名白名单 + MIME + **文件头魔数**三重校验；落盘用随机名、按家庭分目录，不暴露原名
6. **SQL**：全部参数化，无字符串拼接（`text()` 仅用于固定的 `SET FOREIGN_KEY_CHECKS` / `SELECT version_num`）
7. **密钥**：API key 用 Fernet 加密落库，接口只回掩码
8. **日志**：`scrub()` 递归脱敏（密码、token、卡号、证件号、车架号等）
9. **异常**：统一信封，未处理异常只返回通用错误，不泄露堆栈
10. **SSRF**：第三方 AI 与通知 webhook 保存时校验 scheme + 拦截私网/回环/CGNAT
11. **防范意识**：代码注释里能看到历史修复痕迹（如「公开页不暴露服务器绝对路径 L-10」「配置项仅管理员可读 M-3」）

## 八、回归用例

`tests/test_security_endpoints.py`（8 例），针对「改坏了不会报错、只会悄悄泄露」的行为：

1. 已初始化后匿名访问摘要 → 拿不到管理员与家庭名
2. 登录后访问摘要 → 完整
3. 向导阶段（未初始化）→ 完整（否则完成页空白）
4. 只读成员看系统状态 → 审计为空
5. 所有者看系统状态 → 审计正常（不能为了收紧把功能关掉）
6. 无家庭归属查审计列表/详情 → 空结果
7. 无家庭归属列备份 → 空结果
8. 改成员角色传非法值 → 拒绝；合法值 → 生效

`tests/test_rate_limit.py`（17 例），盯「看起来在工作、其实没生效」：

| 组 | 用例 |
|---|---|
| IP 解析（8） | 直连时忽略伪造的 XFF；局域网直连也不能伪造；可信代理取最后一跳；单跳；末项非法退回直连；空对端；配置写错一项不影响其余；掩码只留网段 |
| 窗口计数（4） | 超限后拒绝且给出等待时间；窗口滑过后恢复；不同键独立；桶数量到上限时**放行而不是拒绝**（内存优先） |
| 中间件（5） | 普通接口第 4 次 429；429 带 `Retry-After`；登录阈值更严；不同 IP 分开计数；`/health` 永不限流 |

> 其中「桶数量到上限时放行」这条是刻意反直觉的：限流组件自己不能成为故障源，内存耗尽比限流暂时失效严重得多。
