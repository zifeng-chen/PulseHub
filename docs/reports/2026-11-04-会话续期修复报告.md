# 会话续期缺陷修复报告（2026-11-04）

## 摘要

长时间不操作页面后，切换菜单仍能正常切换，只有手动刷新才会被踢回登录页。根因是**路由守卫只在首次加载时校验会话**，之后不再检查 access token 是否过期。本次把「按 JWT 过期时间静默续期」接进守卫与标签页可见事件，并补上此前完全缺失的会话层测试。

---

## 一、现象

- 页面放着几十分钟（access token 30 分钟过期）后，点击侧边栏菜单**可以正常切换**，没有任何异常。
- 只有手动刷新页面（F5）时，才会跳回登录页。
- 用户预期：「再次操作时应该自动续期；确实失效了才回登录页」。

## 二、根因

`frontend/src/router/index.ts` 的守卫里只有这一段：

```ts
if (!auth.loaded) {
  await auth.loadMe()
}
```

`loadMe()` 会校验会话并在 access 过期时尝试刷新，但它**只在 `loaded === false` 时执行**。首次进入页面后 `loaded` 恒为 `true`，此后所有导航都不再做任何会话校验。

而切换路由本身不产生 API 请求，`api/client.ts` 的 401 拦截器也就没有触发机会 —— 于是形成一个死角：**内存里 `user` 还在、`tokenStore.access` 字符串还在（虽然已过期），守卫认为「已登录」，放行导航**。只有刷新页面会让 Pinia 重置、`loaded` 变回 `false`，才重新走 `loadMe()` 发现过期。

## 三、修复

### 3.1 新增 JWT 过期判断

`frontend/src/api/client.ts`：

```ts
export function isAccessTokenExpiring(bufferSeconds = 60): boolean
```

本地解 JWT payload 的 `exp`（base64url → 百分号编码 → UTF-8 解码，不验签）。**解析失败一律返回 `false`**，交给服务端 401 兜底 —— 绝不能因为一段脏 token 就把用户判成过期并登出。

### 3.2 抽出续期决策（可测试）

新增 `frontend/src/router/session.ts`：

```ts
needsRenewal(): boolean                      // 已登录 且（access 缺失 或 临近/已经过期）
renewSessionIfNeeded(): 'ok' | 'expired'     // 按需续期；失败时清空本地会话
```

抽出的两个理由：

1. 「过期 → 续期 → 失败才登出」是最容易出错的分支，而路由守卫依赖真实 `history` 与懒加载组件、难以在单测里完整驱动；独立成函数后可直接断言。
2. 守卫与 `visibilitychange` 复用同一份判断，避免两套逻辑随迭代漂移。

### 3.3 接入两处触发点

- **路由守卫**（`router/index.ts`）：进入受保护页前调用 `renewSessionIfNeeded()`，返回 `expired` 才带 `redirect` 跳登录。放在「未登录」判断**之前**，使「access 缺失但 refresh 仍在」也能自愈。
- **标签页可见**（`main.ts` 的 `visibilitychange`）：覆盖「切回浏览器标签页、但不切路由」的场景。

### 3.4 续期请求超时

`tryRefresh()` 的 `axios.post` 补 `timeout: 20000`。原因：守卫会 `await` 它，后端无响应时不能把切页无限卡住；而**实测 `/auth/refresh` 偶发 10~11 秒**（见 §7），超时设太紧反而会把「慢但成功」的续期误判为失败、把用户踢下线。

## 四、测试补充

修复前，会话层**没有任何测试**。本次新增两份：

| 文件 | 用例数 | 覆盖 |
|---|---|---|
| `frontend/src/api/client.spec.ts` | 8 | JWT `exp` 解析边界：无 token / 已过期 / 60 秒缓冲临界 / 充裕 / 自定义缓冲 / 无 `exp` / 脏数据不抛错 / 含中文 payload |
| `frontend/src/router/session.spec.ts` | 9 | `needsRenewal` 4 例；`renewSessionIfNeeded` 5 例（有效不发请求 / 过期+续期成功保留会话 / 过期+续期失败清空会话且 `loaded=true` / 无 refresh 不发请求直接 expired / 未登录无副作用） |

`session.spec.ts` 只 mock 网络续期 `refreshAccessToken`，`tokenStore` 与 JWT 解析走真实实现 —— 测的是真实链路，不是替身。

E2E（`deploy/e2e/run.mjs`）补两条**SPA 内切路由**场景（用 `pushState + popstate`，而非整页 `goto`；整页刷新会走 `loadMe` 旧路径，恰好绕开缺陷）：

- access 过期 + refresh 有效 → 切路由自动续期并停留；
- access 过期 + refresh 失效 → 切路由回登录页。

## 五、为什么此前的「全量测试」没发现（测试盲区复盘）

1. **前端单测没有覆盖会话层**。原有 11 个 spec 全是纯函数（utils）、UI 组件（AppModal / AppSelect）、composables、菜单配置、单个 View 的过滤逻辑；`router` 守卫、`auth` store、`api/client` 一个测试文件都没有。
2. **E2E 只测了「完全未登录」**。原 4.8 节是 `localStorage.clear()` 后访问受保护页 → 断言跳登录，验证的是「**没有** token」；缺陷发生在「**有** token 但已过期」，是另一个分支，从未被执行。
3. **缺陷依赖「时间」**。access token 30 分钟才过期，测试秒级跑完，token 永远新鲜，过期分支在测试里**不可能自然触发**——除非显式构造过期 token。
4. **局部正确 ≠ 组合正确**。`loadMe`、401 拦截、守卫单看都对，错的是「`loaded=true` 之后不再校验」这个组合行为，单点测试天然抓不到。
5. **手动测试也难以复现**。开发时连续操作，token 不会过期；要复现得干等 30 分钟或手动改 localStorage。

**结论**：这不是「测了但漏了」，而是「这条链路从未被测试触及」。补测的价值在于把它纳入回归网，而不是事后追责。

## 七、遗留与建议

1. **`/auth/refresh` 偶发 10~11 秒**（11-03 11.3s、11-04 10.5s；11-02 为 139ms）。`refresh_session` 含 3~4 次查询 + 一次 session `UPDATE` 提交，疑似 MySQL 行锁等待或共享库 IO 竞争。当前已用 20 秒超时兜住体验，但**根因未查**，建议后续用慢查询日志定位。
2. **E2E 门禁需要本地后端环境**（`backend/requirements.txt`）。部署脚本 `--step all` 默认先跑 E2E，在未安装后端依赖的机器上需 `--skip-e2e`。
3. 建议把「篡改 token 为过期 → 切路由」这条加入常规回归，任何涉及守卫 / 认证的改动都应跑一遍。
