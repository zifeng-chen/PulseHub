# 数据备份与离线恢复

## 备份里到底有什么

每份备份是一个目录 `/app/data/backups/<备份编号>/`：

| 内容 | 说明 |
|---|---|
| `database.json` | 全部业务表逐行导出（58 张表），datetime / Decimal / bytes 带类型标记 |
| `attachments/` | 附件文件快照 |
| `*.db` | 仅 SQLite 环境额外保存的库文件 |

> 2026-10-17 之前创建的备份**只有附件、没有 `database.json`**，不能用于数据恢复。dry-run 会明确提示。

## 命令

在项目根目录执行（会自动 SSH 到 NAS 并进入 API 容器）：

```bash
# 创建备份（含数据库导出）
python deploy/restore.py --create

# 列出可用备份
python deploy/restore.py --list

# 预览影响范围（dry-run，只读，安全）
python deploy/restore.py --backup BK20261017064857

# 真正执行恢复
python deploy/restore.py --backup BK20261017064857 --yes
```

dry-run 会逐表列出「备份行数 / 当前行数 / 影响」，不写任何数据。

## 恢复做了什么

1. **校验**：备份目录的 SHA-256 必须与创建时一致，否则拒绝
2. **安全快照**：把当前数据导出到 `SAFE<时间戳>`，误执行时还能回来
3. **覆盖**：按表反序清空 → 正序写入，整个过程在单事务内
4. **行数校验**：每张表的实际行数必须等于备份行数，不一致立即回滚
5. **清空会话**：`user_sessions` 只清空不回填 → 所有用户需要重新登录
6. **停站执行**：`--yes` 会先停 `fam-v21-web`，恢复完成后重启 API 与 Web

任一环节失败都会整体回滚，不会留下"半恢复"状态，并写入一条 `failed` 恢复记录。

## 不参与恢复的表

| 表 | 原因 |
|---|---|
| `alembic_version` | 迁移版本由 alembic 维护，不应被旧备份改回去 |
| `backup_records` | 备份清单。覆盖会让恢复后"备份列表变空" |
| `restore_records` | 恢复历史，属于运维审计 |
| `user_sessions` | 清空而非回填，强制重新登录 |

## 注意事项

- **恢复会覆盖用户与权限**，执行后所有人（含管理员）都需要重新登录
- 备份目录是**明文存储**（`encrypted=false` 已如实标记），请确保 NAS 上 `/volume1/docker/fam-v21/backups` 的访问权限
- 建议在数据库迁移、版本升级、密钥轮换前手动 `--create`
- 恢复前务必先跑一次 dry-run，确认「将被覆盖」的表符合预期
