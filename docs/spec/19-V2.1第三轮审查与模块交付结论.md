# 19 · V2.1第三轮审查与模块交付结论

审查日期：2026-10-15

## 1. 本轮审查内容

重新检查了 V2.1 全部文档的页面树、UI、启动引导、业务关系、专项资产、AI、设置、数据库、API、状态机、验收和最终开发指令，并额外检查后续能否按“基座→模块”逐项交付。

## 2. 本轮已修正

- 数据库 ER 图中的 `PROPERTY` 已统一为 `REAL_ESTATE`，避免出现第二套房产主对象。
- 投资实体已统一为 `investment_accounts`，不再出现 `INVESTMENT` 与表清单不一致。
- 基座范围已经从实施计划中独立出来，包括认证、权限、审计、UI、路由、迁移、适配器和错误处理。
- 实施计划已改为基座通过验收后，按核心账务、资产、负债投资、租赁对账、智能录入、工作台洞察、AI通知的顺序逐模块交付。
- 每个模块必须同时交付数据库、API、页面、关联、AI、错误状态和测试，不允许只交页面。

## 3. 当前推荐交付顺序

```text
M0 框架基座
  ↓
M1 核心账务
  ↓
M2 资产与专项资产
  ↓
M3 负债与信用卡 + 投资
  ↓
M4 房产租赁 + 对账
  ↓
M5 智能录入 + OCR
  ↓
M6 工作台 + 洞察
  ↓
M7 本地AI + 第三方AI
  ↓
M8 提醒 + PushPlus + 最终安全验收
```

## 4. 基座必须提前预留的关联

家庭、成员、账户、资产、分类、业务事件、资金变动、附件、审计、AI建议、提醒和提供商配置必须在基座中拥有稳定ID和统一生命周期字段。专项资产、负债、投资、租赁和通知模块只能通过这些ID扩展，不能另起一套家庭、用户、金额或事件模型。

## 5. 当前仍需开发时特别注意的事项

1. `real_estates` 是不动产和房产租赁共用的主对象。
2. 房贷和车贷是负债扩展，不得在资产页面复制贷款余额计算。
3. 车位与房产是一对多关联，解除关联要留审计。
4. 车辆费用必须进入统一业务事件并保留 `vehicle_id`。
5. 水电煤账单可以由OCR/AI识别，但确认前不能进入统计。
6. 贵金属估值必须标明来源和日期，没有来源不能伪造行情。
7. 通知没有后台调度器，只能按文档定义同步发送和手动重试。
8. AI建议必须经过用户确认，确认接口要做权限、版本和幂等校验。
9. 图表、玻璃动效和流光属于表现层，不能改变统计数据和业务事实。
10. 任一未配置的AI、OCR或通知服务都不能阻塞主平台。

## 6. 最终结论

当前 V2.1 文档已具备先完成框架、再逐模块交付的结构。后续开发AI应先交付 M0 基座并等待用户验收，再开始 M1；不得跳过基座直接并行堆叠业务页面，也不得在模块开发过程中擅自改变已确定的实体关系和一级菜单。
